# BreachBrief: Policy Matrix

What happens to each data category before any external model sees it. Legal reasoning in `LEGAL.md`; implementation in `breachbrief/policy.py`, `detectors.py`, `profiler.py`, `agent.py`, `brane_client.py`, and BRANE's team policy in `configure_policy.py`.

Decisions follow the AI-Z brief: **ALLOW**, **PROTECT** (pseudonymise or mask), **LOCAL ONLY**, **BLOCK**, plus **HUMAN ONLY** for decisions the agent may never take.

Two layers enforce every rule (LEGAL.md section 5). **BRANE enforcement** is the action configured in our BRANE team policy "Team-13 / policy-v1" (`allow`, `placeholder`, `local`, `refuse`), or "our code only" where BRANE has no matching rule. **Technical measure** is what BreachBrief does locally before BRANE sees anything (`LOCAL_PREMASK=full`, the default).

The same rules, with the same IDs R1 to R23, are in `policy_matrix_submission.csv` (AI-Z template format).

### Test IDs
- **T1-T5, E1-E5**: the live evidence run against BRANE on 20 November 2026 with policy "Team-13 / policy-v1", in `test_evidence_run.csv` (all 10 PASS). T2, T3, T4 and E3 ran with `LOCAL_PREMASK=guard_only` so that BRANE itself had to act.
- **`file::function`**: pytest unit tests in `tests/`, run offline against a mock gateway (they never call the live endpoint).
- `TEST_PROTOCOL.md` numbers its five AI-Z cases R1-R5. Those are test cases matching T1-T5, not the rule IDs above.

## Minimum requirements check (AI-Z brief)
- At least 3 justified and implemented protection rules: **23 rules**, 14 of them data categories (R1-R14), each enforced by BRANE, by our code, or by both (see the BRANE enforcement column).
- 5 documented test cases: permitted case, protected data, repeated details, bypass attempt, check failure, all automated in `tests/`, plus extra edge cases, and all run live against BRANE as T1-T5 + E1-E5.
- Concrete, verifiable legal sources: see `LEGAL.md`, Sources.
- Synthetic data only: all scenarios are generated by `scripts/generate_data.py`.
